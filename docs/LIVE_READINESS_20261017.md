# 实盘就绪度审计（2026-10-17）

## 结论

- **研究链路：已经融合成一条批处理链。** 收盘后拉数据 → 重建 v5/宽表 → 因子工坊/事件排雷 → 年度重训分数 → 50 只组合 → 账本回放 → 配比 → 纸面前向。每步有快照、sha256、日志、试验台账。
- **实盘链路：没有。** 仓库里搜不到券商接口、实时行情、OMS、交易前风控、券商对账、告警。`scripts/p4_daily.py` 自己写着 "research record only; never trades"；`quantlab/forward.py` 写着 "No brokerage orders are submitted"。
- **"实时"不是这个策略需要的。** 20 日调仓、T+1 开盘成交，盘中毫秒级没有意义。正确的目标是 **T+1 半自动**：收盘后算信号，次日开盘前做盘前检查、下单、对账。

## 上线路径

1. **T+1 半自动（2–3 周）**：盘前检查脚本（停牌/涨跌停/除权/现金/仓位）→ 生成下单清单 → 人工在券商 App 下单 → 收盘后对账。先跑 1–2 个月，单笔 1.4 万元、50 只，人工完全下得过来。
2. **T+1 全自动（再 4–6 周）**：券商 API/OMS、订单状态机、成交回报、交易前风控、kill switch。
3. **监控与运维（再 2–3 周）**：告警、调度、备份、runbook、故障演练。

## 主要风险

- 数据单点：云端 8787，无 failover；某天拉不到数据，流程会停。
- 无 kill switch：出现异常（重复下单、价格带错误）没有一键停。
- QDII 溢价：回测用日频净值，实盘需要实时 IOPV，暂停规则可能误判。
- 除权/停牌/退市：回测按面板处理，实盘要人工核对，尤其是 2024-02 那种流动性事件。
- 纸面账本与真实成交的滑点差异：回测 30bp，实盘首月要按真实成交回填校准。

## 判断

**现在能支撑"每天收盘后出一份纸面组合"，不能支撑"实盘下单"。** 研究侧已经是一个整体；交易侧还是零。要上实盘，先做 T+1 半自动，不要一上来做实时。
