三、方案真正强的地方

这些不是客套。每一条我都对着代码或文档确认过。

  1. 把数据（P1）定为关键路径。整份文档最重要的判断，且是对的。所有其他问题都是它的下游。方案说「数据获取期间可并行开发模型行为测试，绩效结论等待数据验收」——这是正确的资源分配。
  2. 「不把 ETF 样本的成功当成股票选股证据」。对，且很容易搞错。ETF 有穿透、有做市商、没有涨跌停一样的微观结构。
  3. 「保留退市、ST、停牌、行业变更和公司行动记录，不能因缺数据而事后删除表现差的证券」。幸存者偏差说到了点子上。
  4. 「区分事件发生时间、历史可知时间、当前抓取时间和数据修订时间；不得用当前抓取时间伪造历史披露时间」。这是整个项目最深的问题。方案不仅抓到了，还把它变成了可检查的要求（available_at / effective_at / revision 三字段）。
  5. 「供应商声明『完整』必须有可检查的覆盖依据」。与 DATA_PROVIDERS_2026-09-24.md 一致，那份文档写得很诚实——「未使用账号、未采购、未联系供应商」「没有取得授权报价，费用记为『待核验』，不编造报价」。这种自觉比技术细节更难得。
  6. 「随机对照……不用全样本已实现波动事后调平」。微妙且正确。
  7. 「此前 200 次实验……不能证明整个池子没有 Alpha，也不能替代新数据上的实验」。他吸收了我在 R2 里的自我更正。
  8. 「首代不加入 LightGBM。后续需要独立登记，并在同一条件下证明增量」。对的纪律。代码里确实只有 Ridge。
  9. 「市场波动或卖出受阻可能导致实际暴露超限。此时报告超限、禁止增加相关风险并保留退出订单，不能在账面上假装已降仓」。这就是反静默降级原则，被写成了需求。极好。
  10. 「行业样本不足或历史行业身份缺失时，不以当前行业补齐；相应预测返回无效原因」。代码确实这么做（opportunity.py:39 把 'UNKNOWN'/'NA'/'' 映射为 NaN，min_industry_members=5 不足即跳过）。

四、方案的技术缺陷（我的批评）

4.1 「行业扩散」特征组在横截面上没有分辨力

opportunity_features 里，breadth 和 strength 是按行业算出的标量，然后广播给该行业全体成员：

breadth.loc[d,ready]=(close.loc[d,ready]>ma.loc[d,ready]).mean()      # 行业级标量
strength.loc[d,ready]=(rel20.loc[d,ready]>0).mean()                  # 行业级标量

10 个特征里有 4 个（breadth60 / strength20 / breadth_change / strength_change）在给定交易日内对同行业所有股票取值完全相同。一个横截面排序模型从这 4 个特征拿不到任何行业内分辨力，只能得到行业级倾斜。

再叠加 25% 行业上限：模型押的行业倾斜会被配权器系统性地截断——模型想加重仓的行业，恰恰是配权器不让加的那个。

方案说「残差趋势、行业扩散、上涨质量一起验证，暂不宣称是三个独立收益来源」——这不够。应该更进一步：行业扩散在构造上就不可能成为横截面选股来源，它是择时/倾斜的覆盖层。这个判断应该在设计阶段做出，而不是等结果出来后解释「为什么第三个来源没有增量」。

两条出路：(a) 对打分做行业中性化，让行业扩散只影响行业内排序的基准；(b) 把行业扩散组从横截面模型移出，作为独立覆盖层显式建模。二选一，写进方案。

4.2 没有行业中性化

方案引入行业扩散特征，却没有行业中性打分。6% 单股上限 + 25% 行业上限意味着配权器必须跨行业摊开，因此行业级信号会被截断。这与 4.1 是同一个问题的两面：要么中性化，要么移出。

4.3 forward_labels 对公司行动 fail-open

if action.get('action_type','distribution')!='distribution': bad=True;break

action_type 缺失时默认当作 'distribution'（现金/送股），而不是标记异常。这与仓库自己的 fail-closed 原则冲突——evidence.py 缺失即失败、crowding.py 缺失即归未知风险组、allocation.py 缺失行业即具名拒绝。

方案写「无法正确处理的事件明确阻断相关绩效」——代码对「字段缺失」这一类没有做到。一行改动，但它正是方案想消灭的那类缺陷。

4.4 P2 的 1000 次随机对照，现在一次都跑不了

pipeline.run_suite 的第一道门是：

assessment=qualification(ds)
if assessment['status']!='qualified_for_daily_research' and not fixture:
    result=blocked_result(assessment['reasons']); ... ; return assessment

而 qualification() 会因为 historical_industry_incomplete、coverage_evidence_missing:*（6 个字段各需 source_url + verification_artifact + sha256）、historical_universe_required 等理由返回 blocked_data。

方案把 P2 写成独立阶段，但 P2 100% 依赖 P1。在 P1 的真实数据落地前，P2 的执行次数是 0——不是「跑得慢」，是「第一行就返回」。

这个依赖关系必须写明，否则会让人误以为 P2 可以并行推进，进而把「P2 未完成」误判为工程进度问题，而它实际是数据问题。

4.5 折级「净超额」不是独立观测

pipeline.py:106,126：

observed=engine.run(ds,strategy='opportunity',forecasts=all_forecasts,
                    start=folds[0]['test'][0],end=folds[-1]['test'][-1],prepared=prepared)
...
incremental=[float(paired.loc[f['test'][0]:f['test'][-1]].mean()*252) for f in folds]

折级超额是从一次连续运行的净值序列上按日历切片得到的。日历上折不重叠，但持仓跨折延续，所以折级收益不是独立观测。

后果：evidence.py 里「≥3 个不重叠测试段、≥2/3 折扣费增量为正」这条判据，用在这里比它看起来要弱。三个折的符号相关性会显著高于独立情形。

两条出路：(a) 每折独立起账（更保守，但更接近「三次独立实验」的语义）；(b) 保留连续账户，但在文档里明确写明这是「同一账户的连续切片」，并相应降低该判据的权重、把权重移到 ci20/ci60 上。

4.6 缺程序级停止规则 —— 这是最需要补的一条

方案有「每代最多 12 个预登记配置」，但没有「什么时候放弃这条研究路线」。

而且 ExperimentRegistry 的预算上限比它看起来弱得多。pipeline.py:51-52：

identity=fingerprint(dict(protocol=protocol,data=ds.version,config=asdict(cfg),code=provenance()["code_sha256"]))
out=root/identity[:20]; ... registry=ExperimentRegistry(out/'registry',cfg.research)

每个 identity 建一个新注册表。而 identity 包含 data_version、protocol、config 和 code_sha256。

意思是：换数据版本、改协议、调一个参数、甚至改一行代码，都会生成新注册表，试验预算重置为 12。

所以「每代最多 12 个配置」约束的是同一协议下的候选数，不是研究者累计尝试过多少假设。这不是漏洞，但它不是方案以为的那个保护。在 code_sha256 每天都在变的这个仓库里，实际约束接近于零。

要补的：一条跨注册表的累计预算（例如按 data_version 聚合，或单独维护一个全局试验账本），以及一条明确的程序级停止规则——「若第 N 代未过门禁，停止该路线并写出否定结论」。没有后者，方案是一个在无限时间跨度上生成多重比较的机制。

4.7 流程：P0「冻结基线」与「继续写代码」互斥

方案 P0 要冻结基线，P1 又说「数据获取期间可并行开发模型行为测试」。这在逻辑上没问题，但方案漏掉了真正的故障源。

回顾今天：1984edf 提交于 15:54:56，此后 15 分钟内又写了 12 个文件，作者的实现记录 docs/IMPLEMENTATION_2026-09-24.md 停在 15:34，一个字没更新。我在上一轮报告里指出的就是这件事。

方案是一份 5 章、约 40 个行动项的文档。如果不配一条硬规则，它只会放大这个节奏问题：

一个逻辑单元 = 一次提交 + 一次文档更新。不是「阶段结束再提交」，也不是「有空再补文档」。REVIEW_RESPONSE_V3_2026-09-24.md 写得很好——说明他有这个能力，只是没把它变成约束。

因子值高 = 拥挤度低，所以「排名最低的 5%」= 最拥挤的 5%，过滤方向正确。我把不等号读反了，而且值从来没改过——不是「他改了我才发现」，是我一开始就错了。

5.2 「先跑 20 次」的建议 —— 他拒绝得对

我在 R1 里建议「应先跑 20 次」。他的反驳：

「根据初期收益显著性决定是否继续会产生选择偏差。20 次只检查运行质量，不能按结果方向筛选。」

成立。我的本意是「检查仪器是否正常」，但表述成「按初期收益决定是否继续」就是结果依赖的停止规则。pipeline.py:124 的实现方式（只在机制不健康时退出）才是对的。

5.3 R3 的「防护只在配权器」—— 我漏了一层

我上一轮写「contracts.validate() 只查 .isna()，哨兵串 'UNKNOWN' 照样通过，防护只在配权器里」。前半句仍然成立，后半句不准确。

data/qualification.py:16：

missing_sectors = ds.instruments.sector.isna() | ds.instruments.sector.isin(['UNKNOWN','NA',''])
if require_industry and missing_sectors.any(): reasons.append('historical_industry_incomplete')

qualification() 显式检查了哨兵值，而它是 pipeline.run_suite 的第一道门。所以哨兵在研究入口是被拦住的——防护有两层，我说「只有一层」是错的。正确的说法是：validate() 这一层放行，qualification() 这一层拦住，而 allocation() 是第三层兜底。

六、我的建议

  1. 先改第一章的「现状裁定」，再谈执行。5 条 P0 里 4 条已实现、1 条事实错误、1 条与自己的附件矛盾。一份「现状」写错的方案，执行时会把已经做完的事再做一遍，同时漏掉真正的阻塞。
  2. 把 P1 明确写成 P2 的前置条件。现在 P2 是 0 次可运行。写成「P1 完成前 P2 不启动」比写成「可并行」更诚实。
  3. 决定行业扩散组的归属。要么中性化，要么移出横截面模型。这是设计决策，不该留到结果阶段解释。
  4. 补 4.3 那个 fail-open 的一行。action_type 缺失应当阻断，不应默认为 distribution。
  5. 补跨注册表的累计试验预算 + 程序级停止规则。这是方案里唯一一个会导致「看起来有纪律、实际没有」的结构性缺口。
  6. 把「一个逻辑单元 = 一次提交 + 一次文档更新」写成硬规则。技术判断他已经够好，问题从来不在判断力，在节奏。

最后。这份方案的技术判断力，比我在这个仓库里见过的任何一份文档都高。evidence.py 拒绝裸布尔、ExperimentRegistry 按配置而非按折计数、preflight 只看机制不看收益、stress_suite 区分「固定场景」与「事后最不利区间」——这些都是真懂统计和回测陷阱的人才会做的选择。

而且他在 REVIEW_RESPONSE_V3 里抓到了我三处错误，三处都对。一个会核对、会拒绝、会指出审查者错误的对话者，比一个照单全收的对话者有价值得多。

所以我的结论是：方案可以执行，但执行前必须先做一件事——把第一章重写一遍。它的方向对、参数对、判断对，唯独「现在到哪了」说错了。而在一个 15 分钟写 12 个文件的仓库里，「现在到哪了」恰恰是最容易说错、也最不能错的一句。
